## 3. Structure of `main`

`src/main.rs` contains exactly one `fn` item (`fn main`), six local type declarations inside the body of `main`, and one dominant construction expression. No `use`, no `let`, no `mut` bindings, no author `const`/`static`, no `unsafe`, no comments. Attributes are limited to six verified derives (§12).

Local types (all inside `main`, per §8 of the contract — "necessary local type declarations followed by one dominant construction expression"):

| type | derives | purpose |
| --- | --- | --- |
| `enum Destination { Home, Registry }` | `Debug, Clone, Copy, PartialEq` | the two required navigation choices |
| `enum Control { HomeTab, RegistryTab, Launch }` | `Debug, Clone, Copy, PartialEq` | interactive control identities (no `Name` parsing) |
| `enum Role { … 21 variants … }` | `Component, Debug, Clone, Copy, PartialEq` | stable typed role mapping per entity; tab roles carry their `Control` payload |
| `struct Layout { width, height, scale, sidebar_w, pad, 12 × Rect }` | `Clone, Copy, PartialEq` | snapshot of the single layout model, in logical pixels |
| `struct UiState { 15 fields }` | `Resource, Clone, Copy, PartialEq` | the authoritative domain state (§4) |
| `struct UiImages { 9 handles }` | `Resource, Clone` | assets built/loaded once at startup and retained deliberately |

Construction chain: `App::new()` → plugins (`TaskPoolPlugin{…}`, `LogPlugin::default()`, `FrameCountPlugin`, `TimePlugin`, `TransformPlugin`, `InputPlugin`, `AccessibilityPlugin`, `WindowPlugin{…}`, `AssetPlugin{…}`, `WinitPlugin{…}`; then `RenderPlugin{…}`, `ImagePlugin{…}`, `MeshPlugin`, `CameraPlugin`, `PipelinedRenderingPlugin`, `CorePipelinePlugin`, `SpritePlugin`, `SpriteRenderPlugin`, `TextPlugin`) → `Startup` exclusive system → typed `Update` system → `.run()`.

The `Update` system is a single closure with seven typed parameters: `Res<ButtonInput<KeyCode>>`, `Res<ButtonInput<MouseButton>>`, `Query<&Window, With<PrimaryWindow>>`, `Res<Time>`, `ResMut<UiState>`, `ResMut<Messages<AppExit>>`, and one entity query typed `(&Role, &mut Visibility, &mut Transform, Option<&mut Sprite>, Option<&mut TextColor>, Option<&mut TextBounds>, Option<&TextLayoutInfo>)` filtered `Without<Camera2d>`. No system reads state back out of presentation components; the query's mutable items are write targets only.

## 4. Authoritative state (§D mapping)

`UiState` fields ↔ required state:

| required state | field(s) |
| --- | --- |
| selected destination | `selected: Destination` (initial `Home`) |
| HUD visibility | `hud_visible: bool` (initial `false`, F1 edge toggle) |
| hovered control | `hovered: Option<Control>` (only while the window is focused, the HUD is visible, and a cursor position exists) |
| keyboard-focused control + modality | `focused: Option<Control>`, `focus_keyboard: bool` (ring drawn only when both set) |
| pressed/armed pointer control | `armed: Option<Control>` |
| launch state | `launched: bool` — the real transition is preserved |
| Escape hold duration | `hold: f32` (accumulates `delta_secs` while pressed, resets to 0 on release, exit written at ≥ 7.0) |
| layout invalidation inputs | `layout: Layout`, `title_h`, `desc_h`, `measured_settled`, `window_focused`, `last_cursor` |

Animation values: none — transitions are immediate by design (§F permits but does not require them); nothing animates per frame, so settled frames perform zero writes.

Per-frame processing is gated. The gate opens only on: F1/Tab/Enter/Space edges, Escape held, mouse press/release edges, non-zero hold, a pending armed control, unlogged interactive readiness, unsettled text measurement, window focus change, cursor position change, or window logical size / scale-factor change. On idle frames the system reads a few values and writes nothing.

The next state is computed as a pure layered expression chain (measurement → layout → HUD/hold → hover → arm → activation/focus → snapshot write), then one guarded visual pass derives presentation from the new snapshot. Values are compared through non-flagging `Deref` reads and `Mut::into_inner()` is consumed only when the next value differs, so change detection reflects real changes only.

## 5. The single layout model (§E)

One function of `(window logical width, logical height, scale factor, title_h, desc_h)` produces every rectangle, used for **both** sprite/text placement and pointer hit testing — click geometry and displayed geometry cannot diverge because they are the same rectangles. All coordinates are logical pixels, origin top-left, y-down; world placement converts with `((x − w/2)·s, (h/2 − y)·s)` and sprite scale `(s, s, 1)`, so the model is scale-factor aware (high-DPI renders the same logical layout at physical resolution).

Formulas (justified constants in logical px): `sidebar_w = clamp(w·0.26, 180, 340)`; `pad = 16`; app icon `32×32` at `(pad, pad)`; title wrapped to `max(sidebar_w − 74, 60)`; `tabs_top = max(title_h, 32) + 32`; tab rows `56` high, `8` apart, `sidebar_w − 32` wide; tab icon `24×24` inset `(14, 16)`; label inset `50`; focus ring = tab rect expanded `3` on all sides (overlay, never a layout shift); divider = `2` px at the sidebar edge; content region starts at `sidebar_w + 24` with `24` px margins; `card_w = min(content_w, 560)`; card top margin `24`; card interior padding `20`; icon/title row `28`; description wrapped to `card_w − 40`; separator `1` px; launch button `min(card_w − 40, 240) × 56`; badge `116 × 28` top-right of the card; well fills the description+action zone when launched; `card_h = min(173 + desc_h, h − 48)`.

Text measurement: `AppTitle` and `CardDescription` carry `TextBounds` (wrap width from the model); the engine's `TextLayoutInfo.size` (physical px, divided by its own `scale_factor`) is read back while `measured_settled` is false and adopted into `title_h`/`desc_h`, re-running layout until the measurement stabilizes (converges in ~3 frames; the HUD is hidden at startup so the refinement is invisible). No fixed character-width estimate is claimed anywhere; wrapping and placement come from the engine's real text layout.

Minimum-size policy: `resize_constraints` changed from `180×120` to `640×480` logical (the production window is non-resizable borderless fullscreen, so this affects only verification setups; at 640×480 every rectangle remains positive and contained — verified by simulation at 1366×768, 1920×1080, 1280×720, 800×600, 640×480 and five title/desc measurement variants, 25 layouts, all assertions pass). Compact behavior below the sidebar clamp: padding and label wrap widths shrink, text wraps (never truncated by policy), the card shrinks to the content region, and no width goes negative. Production fullscreen behavior is preserved unchanged.

Representative layouts were inspected by faithful Python simulation of the model (`/home/user/arc-parts/verify_rev4.py`, kept outside the maintained tree). Real-application screenshots at 1366×768 under Xvfb+lavapipe are captured by the CI smoke step (§10); runs on physical displays remain NOT RUN in this environment.

## 6. Navigation behavior (§B)

- Initial selection: `Home`. The sidebar shows when the HUD is enabled; on Home no Registry content is displayed, hit-testable, or keyboard-eligible (the group root's derived visibility gates rendering, hit tests filter by eligibility, and the Tab cycle skips ineligible controls).
- Selecting Registry (pointer release inside the tab, or Enter/Space on the visibly focused tab) shows the contained right-hand card. One activation event resolves exactly one control — opening the tab can never activate Launch in the same event.
- Repeated selection changes only `UiState.selected`; entities and assets are never recreated (all 26 spawns live in `Startup`; the policy scan asserts spawn calls exist only before the `Update` registration and that procedural asset construction happens only in `Startup`).
- Returning to Home hides the whole group (no badge, well, border, or empty card remains — hierarchy visibility propagation removes the entire subtree in the same frame) and clears a focused/armed Launch immediately (eligibility cleanup in the same state layer).
- F1 preserves `selected`; restoring the HUD restores the authoritative selection, not a guess from visible sprites.
- Selection is activation-driven only; hover never changes the destination. Keyboard activation of a visibly focused tab is the accessibility equivalent of a click; moving focus does not select.

## 7. Cursor and input (§C)

- Native cursor: `CursorOptions { visible: true, grab_mode: None, hit_test: true }`; no drawn replacement. Cursor rendering is a window-system function; framebuffer captures under Xvfb include the server-side software cursor, which is labeled as X11-specific evidence, not cross-platform proof.
- `window.cursor_position(): Option<Vec2>` is kept optional end to end; `None` ⇒ no hover, no arm, no activation. Nothing fabricates `(0, 0)`.
- All input and metrics come from the primary `Window` (logical px); `Monitor` is no longer referenced by the application.
- Hit areas are the layout model's rectangles — icon, label, and padded body of a tab are one rectangle; overlapping controls are impossible (disjoint rects) and a single hit resolution picks at most one control per event.
- Pointer semantics: press arms the eligible visible control under the cursor; release inside the same control activates; release outside, window focus loss, HUD hide, or eligibility loss cancels the armed control. Focus loss also clears hover and any stale press, so a stored click cannot fire when focus returns (verified by simulation, scenario 10).

## 8. Monochrome styling and focus (§F)

All authored colors are `Color::srgb(g, g, g)` — equal components by construction; alpha via textures only. Palette (grayscale byte values): canvas 0 (clear color), sidebar panel 12, divider/separator 56, card 18, badge 30, well 10; primary text 240, secondary 170, badge label 160; unselected tab body 28 (hover 44, press 20) with ink 225; selected tab body 235 (hover 245, press 215) with ink 20; launch body 235 (hover 250, press 215) with ink 20; focus ring 250 on dark tabs, 15 on the light selected tab. External PNG icons keep their own content, tinted only with grayscale colors.

Six independent states: normal, hovered (pointer position), pressed (armed control), selected (persistent destination), keyboard-focused (ring, drawn only with keyboard modality), disabled. Measured WCAG contrasts (relative-luminance, simulation): label-on-body 13.03:1, selected ink 15.45:1, title-on-panel 17.17:1, description-on-card 8.06:1, badge label 6.38:1 (all ≥ 4.5:1); ring boundaries 16.33:1 and 16.08:1 (≥ 3:1); selected-vs-unselected tab bodies 14.30:1 — no two tabs can read as identically selected. The disabled style value exists in the design space but no shipped control is disabled: Launch has a real supported transition and is preserved per §F; the "Coming Soon" badge is a static label, not a control. Hover/press tint changes are per-entity guarded writes — no texture regeneration, no text resizing, no geometry churn (layout dirtying and interaction styling are separate branches of the same pass).

Focus ring: a separate `ring`-textured sliced sprite per tab, 3 px stroke, drawn over the tab body; visibility derived from `focused && focus_keyboard && hud`; it never changes any control's dimensions or neighbors' positions. Tab/Shift+Tab cycle the eligible controls (`HomeTab → RegistryTab → Launch` when eligible); Enter/Space activate the focused control exactly once per press (Bevy's `ButtonInput::press` ignores auto-repeat for `just_pressed`, so no repeat storms).

## 9. Readiness and interaction signals (§H)

Bounded log lines (all INFO, none per-frame): `ARXUMBRA-STARTUP …` once in `Startup`; `ARXUMBRA-INTERACTIVE selected=… home=x,y,w,h registry=… launch=…` once, at ≥ 2 s elapsed Update time; `ARXUMBRA-LAYOUT …` on each real layout change (resize/DPI/measurement refinement). The control rectangles in these lines are the authoritative hit geometry — the CI harness parses them instead of duplicating layout math, so the harness can never disagree with the application. Process survival alone is never treated as render proof: the smoke gate requires the interactive line (which proves ≥ 2 s of Update frames ran with the renderer initialized) plus scripted interaction results.

## 10. Smoke verification design (§G/§H)

Environment: Xvfb `:99` at 1366×768×24 (the reference viewport of the defect screenshot), lavapipe ICD pinned via `VK_ICD_FILENAMES`, `DISPLAY` exported — matching the enabled `x11` backend (verified feature resolution, not an assumed one). Software-renderer results are reported separately from physical-GPU performance; the adapter line is captured as evidence and labeled lavapipe.

Scripted scenarios (one application run): cold-start capture (HUD hidden) → F1 reveals HUD → Tab shows focus ring → Tab → Enter opens Registry → pointer hover restyles the Home tab → click Home removes the panel → neutral-cursor capture → press Registry, drag out, release (cancel) → capture. Pixel assertions (`compare -metric AE -fuzz 2%`): appearance/disappearance pairs must differ by > 4000 px, ring-only pairs by > 100 px, hover by > 2000 px, and the cancelled-press pair must differ by < 3000 px (cursor pixels only) while differing from the Registry state by > 4000 px. Finally `keydown Escape` must self-exit the process with code 0 within 20 s (proves the ≥ 7.0 s threshold and the exit write), and the log must contain no panic. Screenshots + log are uploaded as the `smoke-evidence-linux-x11-lavapipe` artifact. Native window-manager behaviors (WM decorations, real cursor on physical displays) are out of scope for X11-without-WM and labeled platform-specific.

The twelve acceptance scenarios map: 1 (cold start) — capture `home0`/`home1` + startup log; 2–3 (hover) — `hover1` + AE assertions, hover-never-selects proven in simulation; 4 (press/release outside) — cancel sequence + both AE bounds; 5 (click Registry) — `registry1` via keyboard Enter and pointer paths, Launch-not-activated asserted in simulation; 6 (click Home) — `home2`; 7 (repeated alternation) — simulation ×5 + no-spawn-in-Update policy assertion; 8 (keyboard) — `focus1`/`focus2` + Enter; 9 (stale focus) — simulation (focus cleared on Home return and on HUD hide); 10 (focus loss/regain) — simulation (armed/hover cleared, stored click dead); 11 (resize/DPI) — simulation across five viewports + scale-factor-aware model; real-resize on a live display NOT RUN; 12 (Escape hold/release) — simulation of accumulate/reset/threshold + the real 8 s hold exit-0 in CI.

## 11. Coordinate spaces and asset lifetime

World units = physical pixels (default `Camera2d`, y-up, origin at window center). Sprites: logical `custom_size` × transform scale `(s, s, 1)`. Text: `Text2d` glyph rasterization already applies the render target's scale factor (verified in `bevy_sprite/src/text2d.rs` — `target_scaling_factor` from `RenderTargetInfo`), so text entities use scale `(1, 1, 1)` with world-physical translations, and `TextLayoutInfo.size` (physical px) converts back with its own `scale_factor`. Assets: 3 procedural textures (4×4 solid, 64×64 rounded pill, 64×64 focus-ring stroke — all monochrome, sliced with 16/14 borders for consistent corner radii) + 6 external PNGs, built once in `Startup`, retained via the `UiImages` resource and spawned sprites; nothing regenerates assets after startup.

## 12. Syntax policy and checker boundary (§H)

The CI policy checker (syntax-aware Python, fixtures self-tested every run) enforces: one `fn` (exactly `fn main`), no `use`/`let`/`mut` bindings/author `const`/`static`/`unsafe`/`impl`/raw pointers/interior-mutability types, no comments in maintained `.rs`/`.toml`/`.yml` (block-scalar- and string-aware scanners), balanced brackets, exactly one `src/main.rs`, exact asset tree, exact release matrix/names, pinned action SHAs, no direct wgpu identity in any dependency section, stable semver toolchain pin.

Revision-4 corrections to the checker itself: attributes are no longer blanket-banned — every attribute must be a `#[derive(…)]` whose targets are in a verified allowlist (`Clone, Copy, Debug, Default, Eq, PartialEq, bevy::ecs::component::Component, bevy::ecs::resource::Resource`); inner attributes and all other attribute forms remain violations (fixtures prove both directions). The manifest lint rule no longer hardcodes one allow-list: every lint key must be a named lint (lowercase identifier, never `all`/`warnings`) with an explicit level (`allow`/`warn`/`deny`/`forbid`) — blanket suppression stays impossible without freezing the current set. The `&mut` audit is preserved and strengthened: total count and per-spelling counts are asserted exactly (§13), so the checker cannot silently permit new `&mut` by only distinguishing bindings from references.

## 13. The `&mut` inventory — fresh narrow exception request (§D)

The prior approval covered the rev-3 spellings and explicitly does not carry over. The rev-4 source contains exactly **8** `&mut` spellings, all structurally required by Bevy's public APIs; each is asserted by the policy job:

1. `|world: &mut bevy::ecs::world::World|` — the `Startup` exclusive-system parameter (Bevy's exclusive system signature; no typed-`SystemParam` equivalent exists for one-shot world construction with 26 heterogeneous spawns).
2. `world: &mut bevy::ecs::world::World` — argument of the asset/spawn threading closure inside `Startup` (the no-`let` constraint requires IIFE argument threading to name intermediates).
3. `world: &mut bevy::ecs::world::World` — argument of the Registry-group threading closure (needs the spawned root `Entity` and the world simultaneously).
4. `&mut bevy::camera::visibility::Visibility` — `QueryData` in the `Update` query.
5. `&mut bevy::transform::components::Transform` — `QueryData`.
6. `Option<&mut bevy::sprite::Sprite>` — `QueryData`.
7. `Option<&mut bevy::text::TextColor>` — `QueryData`.
8. `Option<&mut bevy::text::TextBounds>` — `QueryData`.

Items 4–8 are Bevy's only public mutable component access path (`Mut<T>` via query data; all writes go through compare-then-`into_inner()` — no `DerefMut` on a `mut` binding anywhere). Items 1–3 mirror the previously approved exclusive-startup pattern with a smaller count (6 → 3). Status: **approval requested, pending** — until granted, the implementation is reported as noncompliant with the strict no-`&mut` rule, as the contract requires.
